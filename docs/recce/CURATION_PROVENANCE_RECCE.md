# Curation provenance — what Gemma can answer today, and what it would take

Recce, 2026-08-16. Scopes the Gemma-side half of "tell me the history of this
annotation" — what already exists, so the schema conversation starts from facts
rather than assumptions.

**Status, updated 2026-08-16.** It started as a pure recce; two of its three
proposed slices have since landed, so read the status markers rather than
assuming nothing is built:

- ✅ **Evidence reaches the database and comes back out.** The write path carries
  `supportingEvidence` on all three sections; the two blind read VOs surface it.
- ✅ **Snapshot / restore / compare** (§4a) — not in the original plan; it came out
  of "we want a backup before letting an agent apply everything it finds".
- 🟡 **Run linkage** (§6 step 2) — half done. `RUN_SHA` and `AGENT_NAME` landed
  (`8b8f6e1bb9`) and are on production, so the storage question CAB raised is
  settled. What is still missing is the wiring: `RunProvenance` reaches only
  `AnnotationSetsWebService`, so a *curation commit* still cannot say which agent
  run made it. This is the remaining half of "which agent · when".
- ⏳ **A read endpoint** (§6 step 3) — deliberately last, pending an agreed event
  vocabulary.

Driven by three documents that landed the same day:

- `handoffs/UIB_TO_CAB_2026_08_16_TRACE_WHERE_THIS_ANNOTATION_CAME_FROM.md` —
  the UI's proposed trace affordance and event shape. Its closing section
  ("The half that isn't yours") names Gemma's audit trail as a separate ask.
- `handoffs/CAB_TO_UIB_2026_08_16_PROVENANCE_KEY_ON_IDENTITY_NOT_SLUG.md` —
  agrees with the shape, changes the key, and says the two provenance stories
  have to meet at the write-back path.
- `handoffs/CAB_TO_GEMBRO_2026_08_16_GOLD_WRITE_BACK_CASES.md` — that write-back
  path, as an acceptance suite.

Paul's requirement, quoted in the second: *"the current agent output
justifications would be shown; but which agent, when, and was it reviewed by a
human? I don't expect this to be populated by default."*

Three questions — **which agent · when · human-reviewed** — and sparseness is
the design point, not a gap.

---

## 1. What Gemma can answer today

| question | today | granularity |
|---|---|---|
| who changed this dataset, when | ✅ `GET /datasets/{id}/auditEvents` | **dataset** |
| what kind of change | ✅ `DesignChangeEvent` and friends | dataset |
| where did this annotation come from | ✅ `supportingEvidence`, since 2026-08-16 | **annotation** |
| what the value was before | ✅ via a SNAPSHOT (§4a) | dataset, at chosen instants |
| which factor / factor value / tag changed | ❌ | — |
| which agent made this change | ❌ — §6 step 2 | — |
| was a human involved | ⚠️ implicitly (the audit row's actor) | dataset |

Note what the two ✅ additions do and don't buy. Evidence answers "where did this
value come from" at the point it was recorded; a snapshot answers "what did this
dataset look like on Tuesday". Neither answers "who changed *this* annotation,
when" — that still needs per-entity events, and it is the gap the read endpoint
in §6 would close.

`DesignChangeEvent`'s message is a tally, generated by the `@AuditedConditional`
SpEL on `applyDesignChange`:

> `Design replaced via REST: factors +1 / -0, factor values +2 / -1, biomaterial
> assignments changed: 3, analyses removed: 1.`

That is a genuinely useful audit row and a useless provenance record. It cannot
name the factor, and two edits in one commit are indistinguishable.

## 2. Two storage surfaces already exist

**`CHARACTERISTIC.SUPPORTING_EVIDENCE`** (V22) — a per-annotation JSON column,
opaque to Gemma, schema owned by the agents repo. Exactly the right home for
"where did this value come from", and it is already populated by one write path.

It reaches further than "tags" suggests, which is the single most useful fact in
this recce:

- `Statement` **extends** `Characteristic`, so every factor-value statement has
  the column already.
- `ExperimentalFactor.category` **is** a `Characteristic`
  (`ExperimentalFactor:84`), so every factor has one too.

So **a factor needs no new column and no migration.** The claim a factor-level
justification actually makes — "this axis is `cell line`" — is a claim about the
category, and the category is where the evidence belongs. (`ExperimentalFactor.
annotations` is a second characteristic bag, but it is `@Deprecated` and
"effectively always empty"; not a home.)

**`ANNOTATION_SET`** (V20, `61a288d2e7`) — per-`Investigation`, per-run, with
`runId`, `kind`, `source`, `role`, `agentVersion`, `model`, `ranAt`,
`createdBy` / `finalizedBy`, `payloadJson`, `parkedElements`, and a `parent`
chain, behind a live REST surface (`AnnotationSetsWebService`:
`/annotation-sets`, `/{id}`, `/{id}/finalize`, `/{id}/reopen`). It answers
*which agent* and *when* for free, and the `parent` chain is already the
append-only history CAB argues for.

So the two hardest columns are built. What's missing is the wiring.

## 3. The blocker that was: the write path carried no evidence at all — ✅ CLOSED 2026-08-16

The curation side will push through `PUT /datasets/{id}/curation`. That path
drops justification on **every** section:

| DTO | section | carries `supportingEvidence`? |
|---|---|---|
| `TagCommit` | experiment tags | ❌ |
| `SampleCharacteristicCommit` | sample characteristics | ❌ |
| `StatementCommit` | design factor-value statements | ❌ |
| `AnnotationTagInput` | `PUT /datasets/{id}/annotations` | ✅ |

Only the last one — a *different*, single-section endpoint — has the field
(`DatasetsWebService:5230`, written through `tagToCharacteristic` at 5429/5437).
`StatementValueObject` has no such field at any layer, so design statements
have nowhere to put evidence even below the wire.

This is CAB's W13 🛑, and it is broader than they framed it. Their note says
"one write path's `AnnotationDto` drops `supportingEvidence`". The accurate
answer is: the composite commit never carried it, on any section. An annotation
written by the curation side into Gemma today arrives stripped of its
justification and acquires only "modified by the API user" — precisely the
erasure CAB's §"One thing to sequence" warns about.

**This was the smallest change with the largest effect**, and it is done:
`supportingEvidence` is on `StatementCommit`, `TagCommit` and
`SampleCharacteristicCommit`, reaching the entity through `applyStatementFields`
— the chokepoint both create and update already went through. No migration; the
column was always there.

Two properties worth keeping when this is extended:

- **`null` means "no change", not "erase".** A client that carries no provenance
  cannot wipe provenance another client recorded. Anything writing to these
  fields later must preserve that, or the first tool to omit the field silently
  destroys the record.
- **An evidence-only edit is a real change.** Attaching evidence to an otherwise
  identical statement moves no content key, so the no-op short-circuit could not
  see it — the same defect class as the factor description-only edit, one level
  down. `statementEvidenceChanged` closes it. **A no-op check that samples only
  the structure will always drop metadata-only edits** — CAB independently hit
  this on their side; treat it as a pattern, not a coincidence.

CAB's position (`CAB_TO_GEMBRO_2026_08_16_SUBSETS_BLOCK_AND_W13_YES.md`): agreed,
they have added `supporting_evidence` to `StatementD` in their local store, and
they will match whatever shape lands here — field name, nesting, list-vs-object.
They are holding their first batch until it lands, on the reasoning that
re-sending everything later to attach justification is worse than waiting.

Their argument for why **statements** matter more than tags is worth recording,
because it decides the ordering if only one level can be done first: their
composed patterns put the operative claim *in* the statement, not the value.
`astrocyte + derives from part of + spinal cord` — the tissue relationship exists
nowhere else. `Trp53 + has_genotype + Homozygous negative` — two factor values
whose labels are byte-identical and differ only by their statements (our W10
guard, their GSE62625). Evidence hung on the parent value cannot say which
statement it justifies.

### The read half — done 2026-08-16

The column being writable is not enough: the design read path could not surface
it either, so evidence written today would have been write-only.

| read VO | before | now |
|---|---|---|
| `AnnotationValueObject` | ✅ | ✅ |
| `CharacteristicValueObject` — carries a factor's category | ❌ | ✅ |
| `StatementValueObject` — the design read path | ❌ | ✅ |

The parse helper moved to `CharacteristicUtils.parseSupportingEvidence` so the
three surfaces cannot drift; `AnnotationValueObject`'s private copy was retired
in favour of it. On both new fields the value is excluded from
`equals`/`hashCode` (and from `StatementValueObject`'s comparator, which assigns
annotation ids) for the same reason `CharacteristicValueObject.supplementary`
already is: **evidence is provenance, not identity.** The same term reached with
and without recorded evidence is the same term, and including it would silently
split de-duplicated search results in two. Guards in
`CharacteristicValueObjectTest` and `StatementValueObjectTest`.

## 3a. What isn't Characteristic-shaped

Most curation claims are characteristic-shaped and therefore already have a
home. Four classes are not, and should not be forced into one:

| claim | why there's no row |
|---|---|
| a continuous factor value's measurement | carries a `Measurement`, not characteristics — CAB's W3 (24 RIN values) and W14 (six timepoints) have nothing to attach to |
| sample → factor-value assignment | a join-table row; no entity, no id. This is the claim under W6 |
| a deletion | the row is gone, so nothing survives to carry the reason (W2, W3, W12) |
| factor name / description / type | free text on the factor |

The deletion row is the structural finding the tabled TODO already reached: the
most valuable judgments concern entities that do not exist in Gemma. These four
are experiment-level, per-run records — `AnnotationSet`, not a per-entity column
invented for each.

One precedent if a narrow case ever wants to skip that route:
`ExperimentalFactor` already carries `baselineRelevance` +
`baselineRelevanceReason`, scalar curator/agent hint fields mirroring
curation-ui. Non-characteristic curation metadata directly on the factor has
been accepted once.

## 4. On keying: Gemma should key on id, and this is now demonstrated

CAB's argument against `target_id` — it collides, and it is derived from a
mutable label, so a `curator_edited` event orphans the history it exists to
keep — is correct and applies with equal force here.

Gemma does not have the problem, and as of today that is tested rather than
assumed. Two regression guards added to `ExpressionExperimentServiceImplTest`:

- `testApplyAddressesSameCategorySameNameFactorsById` — two factors sharing
  both category and name; an edit addressed by id touches one. (CAB's W9: 20 of
  their 500 experiments carry such a pair.)
- `testApplyAddressesIdenticalLabelFactorValuesById` — two factor values whose
  statements serialize identically; an edit addressed by id touches one. (W10.)

The whole design apply is id-addressed and replace-by-absence. So Gemma's half
of provenance should key on the real entity id — `Characteristic.id`,
`FactorValue.id`, `ExperimentalFactor.id`, `Statement.id` — and the
slug↔id mapping stays a client concern.

One caveat to carry into the joint conversation: CAB notes their FVs are not yet
id-bearing (32 of 3,735). A first slice that is factor-level and tag-level is
therefore clean on both sides; FV-level trace needs their backfill first.

## 4a. Snapshot / restore / compare — ✅ SHIPPED 2026-08-16

Not in the original plan. It came from a different question — *"we want to audit
our old Gemma annotations with the agent and just let it apply everything it
finds, but keep a backup that's easy to restore or compare against"* — and it
turned out most of the machinery already existed.

`AnnotationSetRole.SNAPSHOT` was already modelled as an immutable capture of the
experiment's annotation state at a point in time, append-only, UUID `runId`,
behind `POST /datasets/{id}/annotation-sets`. It is deliberate rather than
automatic — unlike `DRAFT`, which upserts per curator — which is exactly the
"not on every update" property the question asked for. What was missing was a
producer and a way back.

- `POST /datasets/{id}/annotation-sets/snapshot` — the server reads the current
  design, tags, sample characteristics and curation note and stores them.
- `POST /datasets/{id}/annotation-sets/{setId}/restore` — replays it.
- The same call with `?dryRun=true` **is** the compare.

**The design decision that makes the rest fall out: the payload is a
`CurationDocument`** — the shape `PUT /datasets/{id}/curation` already accepts.
So restore is the commit path we already have and compare is the preflight we
already have. Neither needed a second diff implementation that could disagree
with the first.

Restore does two reconciliations first, and they are the reason this had to be
server-side rather than client-composed:

1. **Vanished ids become creates.** An entity whose `gemmaId` no longer resolves
   is re-sent under a `clientRef`.
2. **Entities absent from the snapshot become deletions.** The commit is
   declared-delete, so anything added since has to be named in `deletedIds` or it
   silently survives a "restore" and leaves the dataset matching no snapshot.

🛑 **A restore returns the curation's CONTENT, not its IDENTITY.** Recreated
factor values get fresh ids, and any analysis that survived the intervening run
is cascaded again on the way back. This is pinned as a test
(`testRestoreAfterADeleteReturnsContentUnderANewId`) rather than left in a
comment, because "revert" sounds free and isn't.

**Two bugs this turned up, neither in the new code:**

- **An experiment with any AnnotationSet could not be deleted.**
  `ANNOTATION_SET.INVESTIGATION_FK` carries no `ON DELETE CASCADE`, and
  `ExpressionExperimentWriteServiceImpl.remove` cleaned up subsets, DEAs,
  coexpression, PCA and EE-sets but never annotation sets — so the delete reached
  commit and died on a foreign-key violation. Production, not test-only: any
  dataset an agent has posted a PROPOSAL against was undeletable. Fixed
  service-side, no DDL.
- **`getAnnotations` is the wrong source for a snapshot's `tags` section.** It
  deliberately aggregates experiment tags, design tags and sample tags. Replaying
  the aggregate re-creates every design and sample annotation a second time as an
  experiment-level tag. It surfaced as a 409 only because one annotation happened
  to lack a category; on a fully-categorized dataset it would have duplicated
  silently. Filter on `objectClass == "ExperimentTag"`.

## 5. What "was it reviewed by a human" needs

CAB proposes a computed `review_state` on the read side rather than making every
consumer derive it from the chain. That is the right call and it is cheap for
us: `AnnotationSet` already distinguishes `createdBy` from `finalizedBy`, and
`finalize` / `reopen` endpoints already exist. A set that was finalized by a
human is reviewed; one that was not is not.

The part Gemma cannot answer is *rejection* — an agent proposal nobody accepted
leaves no row here, because nothing was written. That history lives on the
curation-store side (`curation_review_disposition`), which is where CAB says it
already is.

## 5a. There is one client for the write API, and it is CAB

Paul, 2026-08-16, relayed in `CAB_TO_GEMBRO_2026_08_16_KEY_ON_YOUR_SET_ID_CARRY_OUR_RUN_ID.md`:
*"When we start writing to the gemma central, the ui will do that through you so
we don't need them to have two apis."*

The curation UI gets no Gemma write path. It keeps writing to the local store,
and anything bound for Gemma central goes through the agents-side service. Two
consequences for everything below:

- **Design for a single deterministic server-side caller, not a browser.** No
  optimistic-UI concerns, no per-keystroke drafts, no partial-application
  recovery for a user who closed a tab.
- **Every write passes one chokepoint**, which is what makes "arrive with the
  trace already attached" achievable at all. An annotation pushed through that
  one path can carry which agent proposed it and which curator accepted it,
  instead of acquiring a bare "modified by the API user" record that erases both.

## 6. First slice — one of three done, one next, one deferred

1. ✅ **Carry the evidence through the write path.** `supportingEvidence` on
   `StatementCommit`, `TagCommit` and `SampleCharacteristicCommit`, plus the two
   read VOs. Landed 2026-08-16; see §3. CAB has matched the shape on their side
   and is unblocked.
2. ⏳ **Stamp the commit with its run** — contract agreed, **blocked on a schema
   decision**. Accept a run reference on the curation commit and open an
   `AnnotationSet` for it in the same transaction. This is the only one of Paul's
   three questions with no answer at all today.

   CAB settled the key question (`CAB_TO_GEMBRO_2026_08_16_KEY_ON_YOUR_SET_ID_CARRY_OUR_RUN_ID.md`):
   **key on our set id, carry their run reference as attributes.** Never key on
   their `run_id` — it is a human-authored label in a foreign namespace, it is
   1:N against a commit (one run writes many experiments), and it is not stable
   under resume (`resumed_from` / `resume_pass` keep the id and write again).

   Four fields, stored verbatim and returned on read:

   | field | example | `AnnotationSet` today |
   |---|---|---|
   | `runId` | `2026-08-15_allbells147` | ✅ `RUN_ID` |
   | `model` | `claude-sonnet-5` | ✅ `MODEL` |
   | `runSha` | `4d8fdbc` | ✅ `RUN_SHA` — landed `8b8f6e1bb9` |
   | `agentName` | `cell_type` | ✅ `AGENT_NAME` — landed `8b8f6e1bb9` |

   ✅ **The storage half is done (2026-08-16, `8b8f6e1bb9`).** The two columns CAB
   called the ones that carry the answer are now on `ANNOTATION_SET`: `runSha`
   because "we have measured behaviour differences between shas at one model, so
   model alone does not identify the build", and `agentName` because "the agent"
   is a fleet and the useful answer names the specialist. Folding the sha into
   `AGENT_VERSION` was rejected for the reason it looks like — it would have read
   as done while answering the question wrongly.

   They are carried by a `RunProvenance` value object on a new
   `AnnotationSetService.attach()` overload rather than by two more parameters:
   that signature already took eleven arguments, and two more would have made six
   ADJACENT nullable strings — runId, createdBy, agentVersion, model, runSha,
   agentName — where transposing any two compiles silently. The twelve existing
   callers are untouched.

   Both columns were **applied to production by hand on 2026-08-16**;
   `scripts/sql/annotation_set_run_provenance.sql` is the record of what was run
   and why no `db/migration` entry accompanies it. Test and dev get them from the
   Hibernate mapping.

   ⏳ **What remains of this step is the wiring, not the schema.** `RunProvenance`
   reaches only `AnnotationSetsWebService`. The curation commit
   (`PUT /datasets/{id}/curation`) and `PUT /datasets/{id}/design` still accept no
   run reference, so nothing on the curation path fills the columns.

   A second open question rides along: no `AnnotationSetRole` describes an
   *applied write*. The vocabulary is PROPOSAL / DRAFT / SNAPSHOT, and a commit
   is none of them. The column is `VARCHAR(32)` so a new value needs no DDL, but
   it is a shared vocabulary CAB co-owns and should not be extended unilaterally.

   Absorb rather than duplicate: `PUT /datasets/{id}/design` already accepts an
   `agentProposalId` query param and **discards it**, logging a line and a TODO
   pointing at a recce that has since been archived. That is the same idea
   half-built; whatever lands here should replace it, not sit beside it.
3. ⏳ **A read endpoint** — **no longer blocked.** The deferral was pending an
   agreed event vocabulary; CAB reports it settled and shipped on their side,
   served at `POST /rest/v2/datasets/{eid}/provenance/lookup` with uib's client
   reading it. Eight kinds — `imported · agent_proposed · agent_applied ·
   curator_added · curator_edited · promoted · removed · curator_rejected` —
   plus a server-computed `review_state ∈ {unreviewed, accepted, rejected,
   curator_authored, curator_edited}`.

   Two constraints to carry if we adopt it:

   - **`review_state` describes the fate of the PROPOSAL, never the health of
     the annotation.** A `rejected` factor is usually a perfectly good factor
     whose proposed change a curator turned down. uib's first copy read
     "recorded as rejected" beside a sound factor and sent readers hunting for a
     defect that wasn't there.
   - **The writer is deterministic** — a service, never a model call. Recording
     a curation decision must not inherit the latency, cost or flakiness of
     inference.

   Still worth doing after step 2: an event with no run behind it can say what
   changed but not who changed it, which is most of the question.

## Open decisions (carried forward from the tabled TODO)

1. `FRAMING_JSON` + `REVIEW_JSON` as two nullable columns on `ANNOTATION_SET`,
   or one `CURATION_NARRATIVE` with two documented sections.
2. How "the current framing" is read: per-run storage makes it "latest finalized
   AnnotationSet for this investigation" — fine for an agent, awkward for a
   dataset page. Denormalized pointer on the EE, or leave it a query?
3. Whether the tabled `annotations.overall` idea folds in here. It should — same
   experiment-level, mutable, non-tag class of information.
4. Does a design edit that changes no annotation (a factor rename) get a
   provenance event, or only an audit row? UIB's `kind` list has
   `curator_edited`, which suggests yes.
5. ✅ **Settled and implemented 2026-08-16:** stale-anchor subsets **block** with
   `?force=true` as the escape hatch, rather than warning — CAB's call. Their
   argument is this recce's own framing one row down: a cascade-deleted analysis
   is gone, and gone announces itself; an orphaned subset is still there, still
   named, still listed, and now defined by factor values that no longer exist —
   it reads as valid. A false block costs one `force=true`; a false warn costs a
   corrupted subset nobody notices.

   Both force gates now ask one predicate, `DesignPreflightReport.requiresForce()`,
   which also **serializes** so a client never re-derives the rule. The 409 names
   analyses and subsets separately, since they call for different judgment.

   🛑 Implementing it exposed that the detection had never worked. The
   stale-anchor test was `@Disabled` as a "pre-existing failure from PR #1657",
   with a TODO blaming `previewDesignChange`. The real cause was in the test: it
   stubbed `eeDao.getSubSets` while the code reads
   `subSetReadService.getSubSetsWithBioAssays`, so the unstubbed mock returned an
   empty list and no subset could ever be flagged. Stubbing the source the code
   actually reads makes it fire. **A disabled test with a diagnosis in the TODO
   is still an undiagnosed test** — the note was wrong for two months and would
   have made this gate a silent no-op.
